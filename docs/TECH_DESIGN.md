# 技术方案 —— 本地 Markdown 笔记应用

> 状态：技术选型结论 + 总体架构方案，粒度到"可以开工"；实现细节在各功能落地时再细化。
> 功能范围：以 `docs/ROADMAP.md` 为准（P0 核心闭环 → P1 效率增强与全局悬浮窗）。
> 结论：**Tauri 2（Rust 薄壳核心） + Svelte + TypeScript，纯本地 `.md` 文件存储**。

---

## 1. 选型结论与理由

### 1.1 桌面壳：Tauri 2（弃 Electron）

| 维度 | Tauri 2（选） | Electron（弃） |
|---|---|---|
| 安装包 / 常驻内存 | ~10MB / 低（复用系统 WebView） | ~100MB+ / 高 |
| 全局热键 / 托盘 / 置顶无边框多窗口 | 官方插件齐备（`global-shortcut`、`single-instance`、tray 内置） | 同样齐备、更成熟 |
| 开发语言 | 核心少量 Rust；业务逻辑仍以 TS 为主 | 全程 Node/TS |
| 常驻场景契合度 | 高：P1 起"关窗不退、托盘驻留"，内存是真成本 | 可行但资源占用高 |
| 导出 PDF | 需单独评估（见 §8 风险） | `printToPDF` 成熟 |

决定因素：产品定位为**长时间后台驻留**的轻量工具（P1 悬浮窗依赖托盘常驻），Tauri 的低内存与轻体积直接契合；团队可接受少量 Rust，Rust 面严格控制在"薄壳核心"边界内。

### 1.2 前端：Svelte + TypeScript

- Svelte 运行时小、编译产物轻，贴合产品轻量气质；组件模型适合"主窗口 / 悬浮窗"两套独立 UI + 共享组件库的结构。
- TypeScript：共享契约（core ↔ UI 的命令与事件）需要类型约束；现有 `demo/js/*` 的纯函数逻辑可平滑 TS 化复用。
- Markdown 渲染改用成熟库（`markdown-it` + GFM 插件 + Shiki/highlight.js 高亮 + 输出清洗），不再手写解析器；现有 `markdown.test.mjs` 作为渲染行为验收基线迁移到新配置上。

## 2. 总体架构：三层，UI 无状态权威

```
┌─────────────────────────────────────────────────────────┐
│  UI 层（Svelte + TS，每个窗口独立实例）                    │
│   ├─ 主窗口：文件夹 / 笔记列表 / 编辑+预览                  │
│   └─ 悬浮窗（P1）：速记 + 快搜，无边框置顶小窗               │
└───────────────┬─────────────────────────────────────────┘
                │ commands（请求/响应，类型化） + events（广播）
┌───────────────▼─────────────────────────────────────────┐
│  Core 层（Rust 薄壳，单一事实源）                          │
│   ├─ 文件读写：笔记 .md 落盘 / frontmatter 元数据           │
│   ├─ 索引：标题 / 正文纯文本 / 文件夹 / 更新时间             │
│   ├─ 搜索：标题 + 正文                                   │
│   ├─ 动作注册表：快捷键 → 动作 的统一映射                    │
│   └─ 事件总线：文件/索引变更 → 广播给所有窗口                │
└───────────────┬─────────────────────────────────────────┘
                │ Tauri 系统能力（内置 API + 官方插件）
┌───────────────▼─────────────────────────────────────────┐
│  系统：文件系统 / 托盘 / 全局热键 / 多窗口 / 单实例          │
└─────────────────────────────────────────────────────────┘
```

**规则（对应 ROADMAP 的"数据层与 UI 解耦"）**：

- Core 是**唯一事实源**：所有读写、索引、搜索都在 Core；两个窗口之间**不共享前端状态**，只通过事件订阅同一份数据。
- 悬浮窗与主窗口的行为差异只体现在 UI 入口上，底层命令（保存 / 搜索 / 删除）**完全同一套**，不复制逻辑。
- 命令与事件契约集中定义一份（Rust struct ↔ TS 类型），保证两窗口一致。

## 3. 存储与数据模型

### 3.1 笔记文件

- 目录：应用数据目录下的 `notes/`（例：Windows `%APPDATA%\<app>\notes\`），纯本地、天然可备份。
- **一条笔记一个 `.md` 文件**；文件名为稳定 ID（`<id>.md`），文件夹归属等写在 frontmatter，而不是用目录层级表达。
  - 理由：重命名标题 / 移动文件夹只改元数据，文件名与内容地址稳定；避免嵌套目录带来的移动与冲突问题。
- 文件内容示例：

```markdown
---
id: n-xxxxxxxx
folder: 收件箱
title: 示例笔记
tags: []
pinned: false
createdAt: 2026-09-07T10:00:00.000Z
updatedAt: 2026-09-07T10:00:00.000Z
---
# 示例笔记
正文……
```

- P1 新增字段（tags / pinned 已预留占位）不再改存储结构；回收站 / 历史版本届时在元数据或独立目录上扩展，均不破坏既有文件布局。

### 3.2 轻量索引

- Core 启动时扫描 `notes/` 建索引；运行期通过文件变更监听增量更新。
- 索引条目：`id、folder、title、纯文本正文、updatedAt、tags`。
- 删除/重命名通过 Core 统一入口完成，保证文件与索引同步（验收点：删除与重命名正确更新索引）。

### 3.3 搜索

- **起步**：内存索引线性/分词匹配，个人笔记量级足够，即时出结果。
- **演进**：笔记量大后换 SQLite FTS5（rusqlite），只换后端、索引接口不变。
- 搜索对外接口保持稳定：`search(query, folder?) → note 列表`，P1 悬浮窗快搜与主窗口共用。

## 4. Markdown 与编辑器

| 能力 | 方案 |
|---|---|
| 渲染 | `markdown-it` + GFM（任务列表 / 删除线 / 表格 / 代码块语言） |
| 高亮 | Shiki 或 highlight.js（常见语言，P0 要求） |
| 安全 | 输出清洗（白名单过滤），延续 demo 的 XSS 转义回归测试习惯 |
| 待办勾选 | 预览端点击 checkbox → 回写源文（demo 已实现，平移交互 + 测试） |
| 编辑器 | MVP 用 `<textarea>`（对齐 demo）；需要行号 / 代码块内编辑时升级 CodeMirror 6 |

## 5. 窗口与桌面能力

### 5.1 主窗口（P0）

- 三栏布局：文件夹列表 → 笔记列表 → 编辑/预览工作区；编辑/分屏/预览可切换。

### 5.2 悬浮窗（P1 重点）

- 无边框小窗、可拖拽、记忆上次位置；**可置顶**（开关）；`Esc` 隐藏。
- **全局热键唤出/隐藏**：`tauri-plugin-global-shortcut`；键位可配置并持久化，冲突有提示（对应 ROADMAP 验收点）。
- **托盘常驻**：关窗不退出，保证热键随时可用；`single-instance` 插件防多开。

### 5.3 动作注册表（P0 起，为 P1 预留）

- Core 维护一份"动作表"：应用内快捷键（P0）与系统级全局热键（P1）最终都映射到同一批动作（如 `new-note`、`open-quick-search`），**P1 只追加映射、不重构**——呼应 ROADMAP 的预留要求。

## 6. 仓库结构草案（脚手架时再定稿）

```
note-app/
├─ docs/                     # ROADMAP / 本技术方案
├─ src-tauri/                # Tauri 壳：窗口、托盘、插件装配
│  ├─ core/                  # Rust：文件读写、索引、搜索、事件总线（薄壳边界内）
│  └─ commands|events 定义
├─ web/                      # Svelte + TS
│  ├─ src/main/              # 主窗口应用入口
│  ├─ src/float/             # 悬浮窗应用入口（P1）
│  ├─ src/shared/            # 组件 + core-client（命令/事件类型化封装）
│  └─ ...
├─ tests/                    # 纯逻辑回归（现状保留，随迁移演进）
├─ demo/                     # 浏览器原型：交互与验收参考
└─ AGENTS.md
```

- 纯逻辑（索引 / 搜索 / markdown / 待办回写）**全部可脱离壳单测**；Rust core 单测 + TS 侧测试并存，延续"功能落地必须带测试、全绿才交付"的约定（AGENTS.md）。
- `demo/` 保留：作为 P0 交互与验收的可运行参照，待 P0 桌面端功能对齐后再决定去留。

## 8. 风险与待定点

1. **导出 PDF（P1）**：Tauri 打印支持弱于 Electron，落地前需验证方案（WebView 打印 / 生成 HTML 走系统打印等），接口位置提前预留。
2. **WebView 平台差异**：Windows 依赖 WebView2 运行时、Linux 为 WebKitGTK，跨平台渲染与打包需在 CI 覆盖。
3. **Rust 学习曲线**：靠"薄壳核心"边界约束扩散；业务逻辑尽量留在 TS/Svelte 侧。
4. **编辑器演进**：`<textarea>` → CodeMirror 6 是增强而非重写，编辑区组件接口按"可替换"组织。
5. **附件粘贴/拖拽（P1）**：依赖 Tauri 剪贴板/拖放能力，与笔记文件目录的关联规则届时再定。
6. **搜索规模**：FTS5 演进时机以真实笔记量触发，不提前引入。

## 9. 决策记录（简述）

| 决策点 | 结论 | 备选及弃因 |
|---|---|---|
| 桌面壳 | Tauri 2 | Electron：功能成熟但体积/常驻内存高 |
| 前端 | Svelte + TS | React/Vue：生态大但对本产品规模偏重；纯 vanilla：P1 交互复杂度后维护成本高 |
| Markdown | markdown-it 系 | 手写解析器：功能蔓延后风险高、维护贵 |
| 存储 | 每笔记一 `.md` + frontmatter，平铺于 `notes/` | 目录树表达分类：移动/重命名成本高，文件名不稳 |
| 搜索 | 内存索引起步 → FTS5 演进 | 一上来就 SQLite：过早引入复杂度 |
